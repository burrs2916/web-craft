# WebCraft 产品需求定位

> 本文档定义 WebCraft 的产品定位、核心原则和技术边界，作为所有开发决策的基准。
> 任何功能设计、技术选型、交互方案都应与本文档保持一致。
> 最后更新：2026-08-19

---

## 一、产品定位

### 一句话描述

**AI 驱动的个人站点 PaaS —— 本地控制云端，AI 助手辅助开发和运维的动态个人网站平台。**

### 产品形态

- **本地客户端**（Tauri + React）：用户的"驾驶舱"，管理所有站点、连接、运维
- **云端服务器**（用户自备）：站点实际运行的地方，平台统一管理部署和运维
- **AI 助手**：贯穿开发和运维全流程，是核心差异化能力

### 目标用户

- 主要：有云端服务器、想建个人网站/博客/作品集，但不想折腾运维的开发者和内容创作者
- 次要：需要快速搭建多个站点的独立开发者、小团队

## 二、核心原则：钉死核心，开放扩展

**不是二选一，而是分层处理。**

后端和运行时钉死保证体验一致和 AI 效果，前端和内容开放保证用户自由度。

### 🔴 必须钉死的部分（核心体验）

| 模块 | 说明 | 为什么钉死 |
|------|------|------------|
| 数据模型 | 站点、页面、内容块、媒体、用户、权限的核心字段固定 | API 稳定，AI 助手精准工作 |
| 部署运行时 | Nginx + 统一的站点目录结构 + 标准部署流程 | 运维助手才能精准排查和修复 |
| AI 交互方式 | 对话式开发 + 可视化预览 + 独立 AI 窗口 | 核心差异化，体验必须统一 |
| 安全模型 | 沙箱隔离、权限体系、认证方式 | 平台底线，不能让用户乱动 |
| 运维基础设施 | 环境检测、服务管理、日志分析、监控告警 | 平台的核心价值之一 |

### 🟡 可配置的部分（弹性空间）

| 模块 | 说明 | 配置方式 |
|------|------|----------|
| 前端框架 | 默认提供轻量方案，允许用户替换 | 通过主题/模板机制切换 |
| 主题模板 | 提供官方模板，用户可改可从零写 | 模板市场 + 代码级自定义 |
| 数据结构扩展 | 核心字段固定，允许加自定义字段 | 自定义字段配置 |
| API 权限 | 细粒度控制接口对用户代码的开放程度 | 权限面板配置 |
| 第三方服务 | 邮件、存储、CDN 等接入 | 插件/API Key 方式 |

### 🟢 完全开放的部分（用户自由）

| 模块 | 说明 |
|------|------|
| 前端代码 | 用户完全掌控 HTML/CSS/JS，想怎么写怎么写 |
| 静态资源 | 用户自由上传/管理图片、字体、文件等 |
| 内容创作 | 文章、页面、内容块完全由用户控制 |
| 域名绑定 | 用户自备域名，自由配置 |

## 三、为什么是这个方向？

### 1. AI 助手需要确定性

AI 最强大的时候是它**确切知道环境是什么样**的时候。
- 技术栈动态 → AI 每次先"猜"环境 → 效果差 → 用户不信任
- 技术栈固定 → AI 精准操作 → 体验好 → 形成依赖

钉死后端和运行时，AI 运维助手、AI 开发助手的效果才有保障——**这才是核心差异化**。

### 2. 用户想控制的是"外观和内容"，不是"技术细节"

90% 的个人站点用户：
- ✅ 关心：长什么样、写什么内容、能不能快速改
- ❌ 不关心：后端是 Rust 还是 Go、数据库是 SQLite 还是 PostgreSQL

所以后端钉死根本不是问题，**只要前端自由度够**。

### 3. 钉死后端 = 壁垒

如果后端也是用户自选的，那跟 cPanel、宝塔面板有什么区别？跟一个带 AI 的终端有什么区别？

**Rust 写死的后端 + 精准的 AI 助手**，才是护城河。

## 五、功能模块优先级

### P0：核心闭环（必须先跑通）

- [x] 站点管理（创建、列表、配置）
- [x] 远程服务器连接管理
- [x] 运维中心（站点级运维窗口）
- [x] 环境检测（Web 运行环境全面体检）
- [ ] AI 运维助手（对话式运维，通过 terminal_session 驱动）
- [ ] 站点部署（把前端代码推送到云端服务器）
- [ ] 一键建站（AI 生成 → 预览 → 部署 完整闭环）

### P1：体验深化

- [ ] 内容管理系统（页面、文章、内容块）
- [ ] 主题模板系统（官方模板 + 自定义）
- [ ] 域名管理（绑定、SSL 证书自动申请）
- [ ] 性能监控（站点访问速度、资源使用）
- [ ] 安全扫描（漏洞检测、异常登录告警）

### P2：扩展能力

- [ ] 自定义字段（内容模型扩展）
- [ ] API 权限面板（控制哪些接口对用户代码开放）
- [ ] 插件生态（第三方服务集成）
- [ ] 多用户协作（团队版）

## 六、AI 助手体系

AI 是核心差异化，不是锦上添花。每个场景都要有对应的 AI Agent。

| Agent | 场景 | 核心工具 | 状态 |
|-------|------|----------|------|
| 运维助手 | 站点运维、环境排查、服务管理 | terminal_session | 进行中 |
| 环境安装助手 | 服务器初始化、环境搭建 | terminal_session | 已有 |
| 远程桌面助手 | 远程桌面安装与配置 | terminal_session | 已有 |
| 开发助手 | 页面生成、模板定制、前端代码 | file / terminal | 规划中 |
| 内容助手 | 文章写作、内容优化、SEO | notebook / 内容 API | 规划中 |

**AI 设计原则**：
1. 每个 Agent 只专注一个领域，系统提示词精准
2. 上下文自动注入，用户不需要重复说明
3. 工具调用透明，用户能看到执行过程
4. 危险操作需要确认，安全第一

## 七、技术选型原则

### 后端（Rust + Tauri）

- **语言**：Rust（性能、安全、单二进制分发）
- **框架**：Tauri（桌面端）、Axum（云端服务端，如有）
- **数据库**：SQLite（本地）、PostgreSQL/MySQL（云端，用户可选）
- **SSH**：自研连接池 + russh
- **AI Agent**：自研 Agent 引擎 + 多模型支持

### 前端（React + TypeScript）

- **框架**：React 18 + Vite
- **UI 库**：Material UI
- **状态管理**：Zustand / 原生 hooks
- **国际化**：i18next
- **图标**：Phosphor Icons

### 云端运行时

- **Web 服务器**：Nginx（钉死）
- **站点运行时**：静态站点 + 可选的后端服务
- **进程管理**：systemd
- **SSL**：Let's Encrypt + certbot

## 八、反模式（不做什么）

明确"不做什么"和明确"做什么"同样重要。

1. ❌ **不做通用服务器管理面板**——我们不是 cPanel/宝塔，我们是"站点平台"
2. ❌ **不支持任意技术栈**——只支持我们钉死的运行时，保证 AI 效果和运维体验
3. ❌ **不做 SaaS 多租户**——用户用自己的服务器，数据在用户那里
4. ❌ **不做可视化拖拽建站**——我们是"AI 对话式开发"，不是拖拽
5. ❌ **不把后端暴露给用户随意修改**——后端是平台能力，不是用户的玩具
6. ❌ **不追求 100% 灵活**——80% 场景用最优解，剩下 20% 通过扩展机制满足

## 九、决策原则

当遇到技术或产品决策时，按以下优先级判断：

1. **AI 体验优先**——如果一个方案能让 AI 助手更精准，优先选
2. **用户体验第二**——同样效果的方案，选用户操作更少的
3. **运维可靠性第三**——生产环境稳定性比花哨功能重要
4. **开发效率第四**——在不影响前三条的前提下，怎么快怎么来
5. **技术纯度最后**——不为了"优雅"而牺牲前四条
