## 一、运维中心整体架构

### 1.1 架构总览：五层递进模型

WebCraft 运维自动化采用**五层递进架构**，从底层原语到上层业务逐步抽象：

```
┌─────────────────────────────────────────────────────────┐
│ L5 批量执行   同一任务 → N 台服务器，结果聚合对比           │  [设计中]
├─────────────────────────────────────────────────────────┤
│ L4 定时调度   本地调度器 + 系统通知 + 应用启动触发          │  [设计中]
├─────────────────────────────────────────────────────────┤
│ L3 任务编排   多步骤工作流：远程执行/SFTP/条件/重试        │  ✅ 已实现
│              + 运行历史 + 逐步骤日志                       │
├─────────────────────────────────────────────────────────┤
│ L2 运维命令库  参数化脚本（模板+安全校验）+ 12个预置脚本    │  ✅ 已实现
├─────────────────────────────────────────────────────────┤
│ L1 远程执行原语 ssh exec 通道 → 结构化 stdout/stderr/     │  ✅ 已实现
│              exit_code/duration（复用 ControlMaster）    │
└─────────────────────────────────────────────────────────┘
```

### 1.2 前端入口与页面结构

**主入口**：`SiteOpsWindowPage.tsx` — 独立 WebviewWindow 窗口

- URL 参数：`siteId`、`connectionId`、`siteName`
- 从站点卡片（SitesPage）点击「运维」按钮打开
- 顶部标题栏：站点名 + 连接信息（user@host）
- 核心内容：`SiteOpsPanel` 组件

**SiteOpsPanel 四大 Tab**：

| Tab | 标识 | 核心组件 | 功能说明 |
|-----|------|---------|---------|
| 环境检测 | `env` | `EnvCheckPanel` | 调用 `ops-web-env-check` 脚本，展示结构化检测报告 + AI 修复入口 |
| 命令库 | `scripts` | 脚本卡片网格 + `ScriptRunDialog` | 分类侧栏 + 参数化脚本执行 |
| 任务编排 | `tasks` | `TaskEditor` + 任务卡片列表 | 多步骤工作流编排与执行 |
| 运行历史 | `history` | `RunHistory` + `ScriptRunHistory` | 任务历史 + 脚本历史，双 tab 切换 |

**顶部操作区**：
- 渐变色「AI 运维助手」按钮（紫色→蓝色渐变）
- 「AI 环境修复」按钮（环境检测 Tab 内，检测出问题时显示）

### 1.3 核心数据流

```
前端 (React + MUI)
    │
    ▼  Tauri IPC (invoke)
Rust 命令层 (interface/commands/)
    │
    ▼
Rust 服务层 (app/*_service.rs)
    │
    ├─→ SSH ControlMaster 连接池 (infra/ssh/pool.rs)
    │       │
    │       ▼
    │   远程服务器 (OpenSSH)
    │
    ├─→ SQLite 数据库 (infra/storage/database.rs)
    │
    └─→ Tauri 事件系统 (app_handle.emit)
            │
            ▼
        前端事件监听 (listen)
```

## 二、环境检测系统详解

### 2.1 数据结构定义

文件：`src/proto/env-check.ts`

```typescript
// 单项检测状态
type EnvCheckStatus = 'pass' | 'warning' | 'fail' | 'info';

// 单个检测项
interface EnvCheckItem {
  name: string;           // 检测项名称，如 "Nginx"、"内存"
  status: EnvCheckStatus; // 状态
  value: string;          // 当前值，如 "2048M / 4096M (50%)"
  detail?: string;        // 详细说明
}

// 检测分组
interface EnvCheckGroup {
  id: string;             // 分组 ID：system/web/database/cache/ports/ssl/site
  name: string;           // 分组显示名
  items: EnvCheckItem[];  // 该组检测项列表
}

// 检测结果汇总
interface EnvCheckSummary {
  score: number;          // 0-100 综合评分
  total: number;          // 总检测项数
  passed: number;         // 通过数
  warning: number;        // 警告数
  failed: number;         // 失败数
  info: number;           // 信息数
  check_mode?: 'python' | 'bash' | string;  // 检测模式
}

// 完整检测结果
interface EnvCheckResult {
  summary: EnvCheckSummary;
  groups: EnvCheckGroup[];
}
```

### 2.2 检测分组与检测项（7 大分组）

| 分组 ID | 名称 | 检测项示例 |
|---------|------|-----------|
| `system` | 系统基础 | 操作系统、运行时间、CPU、内存、磁盘、Inode |
| `web` | Web 服务 | Nginx 状态、版本、配置检测 |
| `database` | 数据库 | MySQL/MariaDB、PostgreSQL 连接数、数据目录 |
| `cache` | 缓存 | Redis 内存、持久化、连接数 |
| `ports` | 端口监听 | 80, 443, 3306, 5432, 6379, 3001 |
| `ssl` | SSL 证书 | 有效期、颁发者、证书域名（domain 非空时检测） |
| `site` | 站点服务 | webcraft-server 进程、部署路径、项目文件、Nginx 站点配置 |

### 2.3 评分规则

- **pass** 项：100 分
- **warning** 项：60 分
- **fail** 项：0 分
- **info** 项：不计入评分

计算公式：
```
score = (pass × 100 + warning × 60) / (pass + warning + fail)
```

### 2.4 前端展示

文件：`src/components/ops/EnvCheckPanel.tsx`

**展示层级**：
1. 顶部：评分圆环（64px）+ 环境检测标题 + 站点名称 + 检测时间
2. 统计卡片：通过 / 警告 / 失败 / 信息 四项计数
3. 分组折叠面板：7 个分组，每组含多个检测项
4. 状态色：pass=#4CAF50 (绿), warning=#FF9800 (橙), fail=#EF5350 (红), info=#2196F3 (蓝)

**自动触发逻辑**：切换到 env Tab 且有连接时，首次自动触发检测。

**修复前后对比**：支持 `preFixResult` 属性，展示修复前后分数差异。

## 三、AI 修复触发与执行链路

### 3.1 两个专用 AI Agent

后端通过 `ensure_*_agent` 命令**幂等播种**（存在则返回，不存在则创建），各有固定 ID 和专用配置。

#### 3.1.1 运维助手 Agent（Ops Assistant）

- **后端命令**：`ensure_ops_assistant_agent`
- **核心工具**：`terminal_session`（终端会话工具）
- **权限模式**：`permission_mode = "auto"` + `auto_confirm = true`
- **始终允许工具**：`["terminal_session"]`
- **温度**：0.3（偏低，保持准确性）
- **最大迭代**：60 轮

**授权能力范围**（系统提示词定义）：
1. 环境检测：Web 服务器、数据库、缓存、运行时的安装与状态检查
2. 服务管理：Nginx、数据库、Redis 等的重启/重载/启停
3. 日志分析：访问日志、错误日志、系统日志的排查
4. 部署协助：部署目录、文件权限、磁盘空间检查
5. 性能排查：CPU/内存/磁盘/网络瓶颈分析
6. 安全检查：端口监听、防火墙、登录日志
7. 日常维护：磁盘清理、数据备份、包更新（需用户确认）

#### 3.1.2 环境修复助手 Agent（Env Fix Assistant）

- **后端命令**：`ensure_env_fix_assistant_agent`
- **专用场景**：环境检测问题的诊断与修复
- **输入**：环境检测报告 JSON
- **输出**：修复方案 + 终端执行

### 3.2 AI 修复触发链路（以环境修复为例）

文件：`src/components/ops/SiteOpsPanel.tsx` → `handleAiEnvFix`

```
用户点击「AI 智能修复」按钮
    │
    ▼
1. 保存当前检测结果为 preFixEnvResult（用于后续对比）
    │
    ▼
2. 创建 SSH 终端会话
   spawnTerminal(sessionId, { connection_type: 'ssh', ssh: sshInfo })
    │
    ▼
3. 确保环境修复助手 Agent 存在（幂等播种）
   ensureEnvFixAgent(modelId, lang) → agentId
    │
    ▼
4. 序列化检测报告为 JSON
   checkReportJson = JSON.stringify(envResult)
    │
    ▼
5. 打开 AI Copilot 独立窗口
   openAiCopilotWindow({
     scene: 'envFix',
     agentId,
     sessionId,
     host, username,
     siteName, remotePath, domain,
     checkReport: checkReportJson,
     dbType
   })
    │
    ▼
6. AI Copilot 页面加载 Agent + 终端会话
   → Agent 读取检测报告
   → 通过 terminal_session 工具执行修复命令
   → 实时输出到前端对话界面
```

### 3.3 terminal_session 工具能力

`TerminalSessionTool` 是 AI 运维的核心执行通道：
- 操作**已建立的 SSH 终端会话**（前端传入 session_id）
- 支持 `write` 动作（写入命令）和 `read_output` 动作（读取输出）
- sudo 密码由终端会话自动应答，Agent 可直接使用 sudo
- 内置安全黑名单拦截危险命令

### 3.4 安全防护机制

1. **危险命令黑名单**（执行层硬拦截）：
   - `rm -rf /`、`mkfs`、`dd if=`
   - fork bomb、`shutdown`、`reboot` 等
2. **提示词软约束**：系统提示要求高风险操作先解释影响并请求用户确认
3. **全链路日志**：`appendEnvOpsLog` 记录每个阶段的 INFO/ERROR 日志

### 4.2 数据结构

```typescript
// SFTP 目录条目
interface SftpEntry {
  name: string;
  is_dir: boolean;        // lstat 真值（符号链接不算目录）
  is_symlink: boolean;    // 是否为符号链接
  target_is_dir: boolean; // 可进入性（目录或指向目录的符号链接）
  size: number;           // 文件大小（字节）
  mtime: string;          // 格式化的修改时间
  mtime_ts: number;       // 修改时间戳（epoch 秒）
  perms: string;          // 权限字符串
  owner: string;          // 所有者
  group: string;          // 所属组
  link_target: string | null;  // 符号链接目标
}

// 传输进度事件
interface SftpProgressPayload {
  transferId: string;
  file: string;
  percent: number;
  transferred: string;    // 已传输大小（格式化）
  rate: string;           // 传输速率
  eta: string;            // 预计剩余时间
}
```

### 4.3 进度事件

- **事件名**：`sftp-progress`
- **订阅方式**：`onSftpProgress(handler)` → 返回 `UnlistenFn`
- 实时推送传输进度、速率、ETA

### 4.4 底层实现

- **Unix 平台**：基于 OpenSSH 的 `ControlMaster` 连接池复用已认证连接
- **Windows 平台**：交互式 sftp 回退模式
- **批量列表**：`sftp_list_many` 单次会话获取多个目录，减少 N 次往返
- **断点续传**：upload/download 均支持 `resume` 参数，后端比较文件大小后续传

## 五、连接管理系统

### 5.1 数据模型

文件：`src/proto/connection.ts`

```typescript
// 连接配置（存储在数据库中的记录）
interface ConnectionConfig {
  id: string;                 // 唯一 ID

  host: string;                           // 主机地址

  username: string;                       // 用户名
  auth_method: 'none' | 'password' | 'private_key';  // 认证方式
  private_key_path?: string;              // 私钥文件路径（密钥认证时）
  password?: string;                      // 密码（密码认证时）
}
```

### 5.2 管理 API

文件：`src/core/services/connection.service.ts`

| 函数 | 后端命令 | 说明 |
|------|---------|------|
| `listConnections()` | `list_connections` | 获取所有连接列表 |
| `saveConnection(config)` | `save_connection` | 新增或更新连接 |
| `deleteConnection(id)` | `delete_connection` | 删除连接 |
| `testConnection(ssh, timeoutMs?)` | `test_connection` | 测试连接可用性（含客户端超时兜底） |

### 5.3 安全特性

- **密码加密存储**：应用启动时初始化加密密钥（与数据库同目录）
  - 位置：`infra/security/crypto.rs` → `init(effective_data_dir)`
  - 失败时降级为明文存储，不阻断启动
- **密码不落盘到前端**：终端标签页持久化时排除 password 字段
- **密码认证的 SSH 会话无法自动恢复**：重启后密码认证的会话不自动重连

### 5.4 ControlMaster 连接池

文件：`src-tauri/src/infra/ssh/pool.rs`

- **原理**：基于 OpenSSH 的 `ControlMaster` 多路复用机制
- **复用方式**：首次连接创建主连接，后续 SFTP/远程执行复用同一认证通道
- **空闲回收**：240 秒空闲后自动回收
- **保活间隔**：20 秒
- **按 lane 隔离**：不同功能（sftp/exec）使用不同 lane 避免冲突

### 5.5 连接状态管理

- **活跃连接追踪**：`useConnectIntent` store 追踪当前使用中的连接
- **站点卡片连通探测**：SitesPage 自动探测绑定服务器的连通性（8s 超时，结果缓存）
- **已部署站点健康探测**：通过 `/healthz` 端点检测部署服务状态（3s 超时）

### 7.2 脚本执行流程

```
用户选择脚本 → 表单渲染参数 → shell-safe 模板渲染 → 安全黑名单校验
    → danger 等级确认弹窗 → L1 RemoteExecService 执行
    → 结果返回 + 历史记录落库
```

### 7.3 安全特性

1. **Shell 安全转义**：`render_template_shell_safe()` 对参数做安全转义
2. **未解析占位符阻断**：检测 `{{` 残留，未填参数的脚本禁止执行
3. **危险命令黑名单**：`rm -rf /`、`mkfs`、`dd if=`、fork bomb、`shutdown`、`reboot` 等
4. **三级危险等级**：
   - Safe：无确认，直接执行
   - Careful：需用户确认弹窗
   - Dangerous：需确认 + 红色标记警示

### 7.4 存储机制

- **表**：`ops_scripts`（脚本定义）+ `ops_script_runs`（执行历史）
- **预置脚本**：应用启动时 `ensure_builtins()` 幂等播种
  - `is_builtin=true` 标记只读，不可删除/修改，仅可停用
- **用户脚本**：可增删改，`is_builtin=false`
- **执行历史**：每脚本最多保留 100 条（`MAX_SCRIPT_HISTORY`），自动修剪

## 八、自动化任务编排系统（L3）

### 8.1 任务定义模型

文件：`src/proto/automation.ts`

```typescript
interface AutomationTask {
  id: string;
  name: string;
  description: string;
  connection_ids: string[];     // 支持多连接（L5 批量基础）
  steps: TaskStep[];            // 步骤列表
  retry?: RetryConfig | null;   // 全局重试配置
  notify: boolean;              // 完成通知
  run_on_startup: boolean;      // 启动补跑
  enabled: boolean;
  last_run_at?: number | null;
  created_at: number;
  updated_at: number;
}
```

### 8.2 步骤类型（5 种）

| 步骤类型 | 说明 | 状态 |
|---------|------|------|
| `remote_exec` | 远程 SSH 命令执行 | ✅ 已实现 |
| `local_shell` | 本地 shell 命令 | ✅ 已实现 |
| `sftp_transfer` | SFTP 文件上传/下载 | ✅ 已实现 |
| `delay` | 等待秒数 | ✅ 已实现 |
| `local_build` | SSG 构建 | ❌ 占位，返回"尚不支持" |

### 8.3 步骤编排能力

1. **顺序执行**：按索引顺序执行
2. **条件分支**：`StepCondition` 三选一
   - `on_success`（默认，仅前序成功时执行）
   - `on_fail`（仅前序失败时执行，用于回滚）
   - `always`（无论成功失败都执行）
3. **步骤级重试**：`RetryConfig { maxAttempts, backoffSecs }`，指数退避
4. **断言验证**：
   - `expectStdout`：stdout 需包含指定字符串
   - `expectStderr`：stderr 需包含指定字符串
   - `expectExitCode`：退出码需等于指定值
5. **失败继续**：`continueOnFail` 标记，步骤失败不中断整个任务
6. **超时控制**：每步骤独立 `timeoutSecs`
7. **运行取消**：`CancellationToken` 支持中途取消
8. **单实例锁**：同一任务同时只允许一个运行实例

### 8.4 运行历史

- `task_runs` 表：每次运行记录（触发方式、起止时间、状态、耗时、错误摘要）
- `task_run_steps` 表：逐步骤日志（命令原文、渲染后命令、stdout/stderr、exit_code、断言结果、重试次数）
- 输出截断：stdout/stderr 各保留头 256KB + 尾 256KB

### 8.5 实时事件

通过 Tauri 事件向前端推送进度：
- `task-step-started`：步骤开始
- `task-step-finished`：步骤完成
- `task-run-finished`：整个任务完成

## 十、当前缺口与建议

### 10.1 已识别的缺口

1. **检测结果与修复动作无关联**：用户看完检测报告后需手动去脚本库找对应脚本
2. **无「一键修复」入口**：缺少单项目修复和批量修复能力
3. **L4 定时调度未实现**：cron 调度 + 系统通知
4. **L5 批量执行未实现**：多服务器并行 + 结果聚合对比
5. **修复后自动复检机制缺失**：修复后需要手动重新检测
6. **`local_build` 步骤类型占位**：自动化任务中的 SSG 构建步骤未实现

### 10.2 建议实施路径（参考 ops-infra-analysis.md）

**Phase 1（快速落地）**：脚本映射 + 一键修复
- 在检测脚本中为常见问题增加 `fix_script_id` 映射
- EnvCheckPanel 增加单项目一键修复按钮
- 修复后自动刷新该项/全量复检

**Phase 2（体验升级）**：叠加 AI 智能修复
- 已具备技术基础（EnvFixAgent + 检测报告传入）
- 当前已打通但需要完善 UI 交互和结果对比展示

**Phase 3（体系化）**：修复任务模板
- 建立修复规则库
- 用自动化任务编排复杂修复流程
