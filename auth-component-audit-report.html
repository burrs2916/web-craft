审查范围：7 个认证组件 × 三层架构（configSchema / renderer / codegen）+ websiteAuthStore + HttpAdapter  |  审查时间：2026-09-10

核心结论：7 个认证组件目前无法形成完整闭环

登录→守卫→用户信息→登出主链路基本通畅，但 Token 刷新链路存在 3 处断裂，存储键命名存在系统性不一致（expiresAt 键名在不同组件中不同），memory 存储模式下各 codegen IIFE 的 memoryCache 互相隔离导致跨组件状态不可见。这 3 个 P0 级问题会在特定配置下导致认证状态断裂。

二、事件流图

4 个自定义事件构成认证组件间的通信骨架。以下逐个分析每个事件的触发→消费路径，标注断裂点。

事件 1：auth-state-change 主链路

编辑态（renderer → store → renderer）
LoginForm Renderer → setLogin() → auth-state-change → AuthGuard → UserProfile → LoginForm（自隐藏）
发布态（codegen IIFE → IIFE）
Login Codegen → dispatchEvent → auth-state-change → AuthGuard Codegen → UserProfile Codegen → LoginForm Codegen（自隐藏）
LogoutButton → logout() → auth-state-change → AuthGuard → fallback → UserProfile → 未登录

✓ 通畅 auth-state-change 是最核心事件，编辑态和发布态的触发→消费链路完整。所有登录组件（LoginForm/RegisterForm/OAuth/SSO/ApiKey）通过 setLogin() 或直接 dispatch 触发，AuthGuard 和 UserProfile 监听消费。

事件 2：webcraft-show-login 通畅

AuthGuard（未认证） → webcraft-show-login → LoginForm（显示/滚动）

✓ 通畅 AuthGuard 在 onUnauthenticatedAction="dispatchEvent" 时触发，LoginForm 监听后 form.style.display = "flex" + scrollIntoView。编辑态 renderer 也实现：AuthGuard dispatch → LoginForm useEffect 监听 setVisible(true)。

事件 3：webcraft-token-expired 断裂

AuthGuard Codegen → webcraft-token-expired → LoginForm Codegen ✗ HttpAdapter（不监听）

✗ 断裂 AuthGuard 检测到 token 过期时 dispatch webcraft-token-expired，但消费方只有 LoginForm codegen 的 performRefresh()。HttpAdapter 不监听此事件（grep 确认 HttpAdapter.ts 中无任何 addEventListener），导致非 LoginForm 场景下的 token 过期无法触发自动刷新。详见 问题 #4。

事件 4：webcraft-token-refreshed 断裂

LoginForm Codegen → webcraft-token-refreshed → AuthGuard Codegen ✗ HttpAdapter（不 dispatch）

✗ 断裂 LoginForm codegen 刷新成功后 dispatch webcraft-token-refreshed，AuthGuard codegen 监听后 updateGuard(true)。但 HttpAdapter 的 tryRefreshToken() 成功后不 dispatch 此事件（grep 确认 HttpAdapter.ts 中无任何 dispatchEvent），导致 HttpAdapter 触发的刷新无法通知 AuthGuard 更新 UI。详见 问题 #5。

四、问题清单（18 条）

P0 级 — 闭环断裂 / 安全风险

#1 expiresAt 存储键名不一致导致 AuthGuard 过期检查永久失效

P0
所有登录组件（LoginForm/RegisterForm/OAuth/SSO）写入 __webcraft_auth_expires_at，但 AuthGuard codegen 在 checkAuth() 中读取 storage.getItem("expiresAt")（auth.ts:1483）。键名不匹配，expiresAt 变量永远是 parseInt("0") = 0，条件 expiresAt > 0 && Date.now() >= expiresAt 永远为 false，导致 JWT token 过期检查永久失效。
auth.ts:1079 setCachedValue("__webcraft_auth_expires_at", String(expiresAt)); ← Login 写 auth.ts:1483 var expiresAt = parseInt(storage.getItem("expiresAt") || "0", 10); ← Guard 读 ← 键名不匹配！
修复：将 auth.ts:1483 的 "expiresAt" 改为 "__webcraft_auth_expires_at"。同时检查 store 侧 setLogin（websiteAuthStore.ts:552）也写入 "expiresAt" 而非 "__webcraft_auth_expires_at"，需统一。

#2 codegen 各 IIFE 的 memoryCache 互相隔离，memory 存储模式下跨组件状态不可见

P0
每个 codegen 函数生成独立 IIFE，各自声明 var memoryCache = {}（auth.ts:688, 1957 等）。在 tokenStorage: "memory" 配置下，LoginForm 写入的 token 只存在于 Login IIFE 的 memoryCache 中，AuthGuard/UserProfile/LogoutButton 的 IIFE 各有自己的 memoryCache，读不到对方写入的值。getStorage() 返回 null，导致所有读写都走 memoryCache，但各 IIFE 的 memoryCache 不共享。
auth.ts:688 var memoryCache = {}; ← Login IIFE auth.ts:1718 function getCachedValue(key) { ... storage.getItem(key) } ← UserProfile IIFE，无 memoryCache！ auth.ts:1957 var memoryCache = {}; ← Logout IIFE
修复：在 codegen 生成代码中，将 memoryCache 提升到全局作用域（window.__webcraft_memory_cache = window.__webcraft_memory_cache || {}），所有 IIFE 共享同一个对象。或改为在 tokenStorage: "memory" 时 fallback 到 sessionStorage，避免内存隔离问题。

#3 UserProfile codegen 在 memory 存储模式下无法读取用户信息

P0
UserProfile codegen 的 getCachedValue(key)（auth.ts:1718-1722）只从 storage 读取，没有 memoryCache。当 tokenStorage: "memory" 时，getStorage() 返回 null，getCachedValue 恒返回 null，导致 UserProfile 永远显示"未登录"，即使 Login 已经成功登录。这是 #2 的直接后果，但影响面更广。
修复：统一 UserProfile codegen 的 getCachedValue 实现，加入全局 memoryCache 支持（与 #2 修复联动）。

#4 HttpAdapter 不监听 webcraft-token-expired 事件，token 过期后无法自动刷新

P0
AuthGuard codegen 检测到 token 过期时 dispatch webcraft-token-expired（auth.ts:1489），期望触发刷新。但 HttpAdapter 的 tryRefreshToken() 只在 HTTP 401 响应时被动触发（HttpAdapter.ts:155），不监听 webcraft-token-expired 事件。发布态下只有 LoginForm codegen 的 performRefresh() 监听此事件——但如果页面上没有 LoginForm 组件（比如只有 OAuth + AuthGuard），token 过期后无人刷新。
HttpAdapter.ts: grep "addEventListener" → 0 results auth.ts:1337 window.addEventListener("webcraft-token-expired", function(e) { performRefresh() }) ← 只有 LoginForm
修复：在 codegen 产物中注入一个独立的 token 刷新 IIFE（不依赖 LoginForm），或在 AuthGuard codegen 中内联 refresh 逻辑（fetch refreshEndpoint → setCachedValue → dispatch webcraft-token-refreshed）。方案二更简单：AuthGuard codegen 已有 dispatch 逻辑，在 dispatch 前直接执行刷新。

#5 HttpAdapter 刷新成功后不 dispatch webcraft-token-refreshed 事件

P0
HttpAdapter 的 tryRefreshToken() 成功后调用 authState.setToken(newToken)（HttpAdapter.ts:288），而 setToken 内部只 dispatch auth-token 事件（websiteAuthStore.ts:579），不 dispatch webcraft-token-refreshed。AuthGuard codegen 监听的是 webcraft-token-refreshed（auth.ts:1603），不是 auth-token，因此 HttpAdapter 触发的刷新无法通知 AuthGuard 更新 UI（守卫不会从 fallback 切换回内容显示）。
HttpAdapter.ts:288 authState.setToken(newToken); ← 内部 dispatch "auth-token" 而非 "webcraft-token-refreshed" auth.ts:1603 window.addEventListener("webcraft-token-refreshed", function(e) { updateGuard(true); }); ← Guard 等的是这个
修复：在 HttpAdapter.tryRefreshToken() 成功分支（HttpAdapter.ts:298 后）追加 window.dispatchEvent(new CustomEvent("webcraft-token-refreshed", { detail: { token: newToken } }))。或在 store 的 setToken 方法中追加 dispatch。

#6 LoginForm basic auth 模式 expiresAt:0 传入 setLogin 导致 renderer 侧判定立即过期

P0
LoginForm renderer 在 basic auth 模式下调用 setLogin({ token: credentials, user, expiresAt: 0 }, "basic")（LoginFormRenderer.tsx:479）。虽然 checkExpired(0) 返回 false（websiteAuthStore.ts:338），但这依赖于 checkExpired 的 !expiresAt || expiresAt === 0 短路。如果将来有人改 checkExpired 的逻辑（比如 expiresAt <= 0），basic auth 会立即过期。此外 codegen 侧 LoginForm 写入 __webcraft_auth_expires_at 的值为 "0"，AuthGuard 读到 0 后 expiresAt > 0 为 false 跳过过期检查——行为正确但依赖隐式约定。
修复：LoginForm renderer basic 模式不传 expiresAt（undefined），与 ApiKeyConfig renderer 的修复保持一致。codegen 侧 basic 模式不写 __webcraft_auth_expires_at。

P1 级 — 逻辑不一致 / 边界缺陷

#7 LogoutButton codegen 不清除 OAuth/SSO 的 state 和 PKCE verifier

P1
OAuth codegen 将 __webcraft_oauth_state 和 __webcraft_pkce_verifier 存入 sessionStorage（auth.ts:2471, 2482）。SSO codegen 将 __webcraft_sso_state 存入 sessionStorage。但 LogoutButton 的 clearAuthCache() 只扫描 getStorage() 返回的 storage（由 tokenStorage 配置决定），如果 tokenStorage 是 localStorage，sessionStorage 中的 state/verifier 不会被清除。这些残留的 state/verifier 在下次 OAuth/SSO 登录前可能被误用。
修复：LogoutButton codegen 的 clearAuthCache() 追加清除 sessionStorage 中的 __webcraft_oauth_state、__webcraft_pkce_verifier、__webcraft_sso_state。

#8 ApiKeyConfig renderer 写入 __webcraft_auth_mode 为 "api-key"，但 store 的 WebsiteAuthMode 类型有 "api-key"

P1
Store 类型定义 WebsiteAuthMode = "session" | "jwt" | "basic" | "oauth" | "sso" | "api-key" | "oauth2"（websiteAuthStore.ts:29），ApiKeyConfig renderer 传 "api-key" 是合法的。但 AuthGuard codegen 的 checkAuth() 只识别 "basic" 和 "session" 两个特殊模式（auth.ts:1471-1478），"api-key" 走默认的 JWT 分支（检查 token 存在 + 过期检查），而 API Key 不应该有过期检查（ApiKeyConfig 不写 expiresAt）。虽然 checkTokenExpiry 配置为 true 时会读 expiresAt = 0 然后跳过（0 不触发过期），但这是隐式正确。
修复：AuthGuard codegen 的 checkAuth() 追加 if (authMode === "api-key") { return authFlag && !!token; } 分支，与 basic 模式同等处理。

#9 RegisterForm renderer 的 authMode 传值不精确

P1
RegisterForm renderer 在 autoLogin 后调用 setLogin(result, tokenStorage === "memory" ? "session" : "jwt")（RegisterFormRenderer.tsx:186）。如果用户注册后实际是 OAuth/SSO 流程，authMode 被设为 "jwt" 或 "session" 而非 "oauth2"/"sso"。这会影响 AuthGuard 的模式感知检查和 HttpAdapter 的 header 构建（basic 模式用 Basic 前缀，其他用 Bearer 前缀）。
修复：RegisterForm 的 autoLoginAfterRegister 应增加 authMode 配置字段（或在 config 中加 autoLoginMode），不硬编码 "jwt"/"session"。

#10 SSOButton codegen 的 token 交换请求缺少 Content-Type header

P1
SSOButton codegen 的 token 交换 fetch（auth.ts 约 2990 行附近）发送 application/x-www-form-urlencoded 格式的 body，但 renderer 侧（SSOButtonRenderer.tsx:122-124）设置了 Content-Type: application/x-www-form-urlencoded。需确认 codegen 侧同样设置了此 header——查看 grep 结果 auth.ts:3003 附近确实有设置，但 SAML 协议的 token 交换可能需要不同的 Content-Type（部分 SAML IdP 要求 application/soap+xml）。
修复：SSO codegen 按 protocol 分支设置 Content-Type：OIDC 用 application/x-www-form-urlencoded，SAML 用 application/soap+xml 或配置驱动。

#11 AuthGuard renderer 编辑模式 fallback 覆盖内容区但不阻止子组件交互

P1
AuthGuard renderer 编辑模式下 showFallback = isEdit || !isAuthenticated（AuthGuardRenderer.tsx:100），fallback 用 position: absolute, opacity: 0.55, pointerEvents: "none" 覆盖在内容区上方。虽然 pointerEvents:none 不拦截交互，但视觉上 fallback 的背景色会遮挡子组件。与其他认证组件（RegisterForm/SSO/ApiKey）"编辑模式与预览一致"的约定不同——AuthGuard 编辑模式有虚线边框和路由守卫徽章。
修复：这是 AuthGuard 作为容器组件的特殊性，徽章和虚线边框是合理的。但 fallback 的 opacity 可以从 0.55 降到 0.3，减少视觉遮挡。或改为只显示 fallback 文字标签，不覆盖背景色。

#12 LoginForm renderer 的 getWebsiteAuthState() 在 useEffect 外调用导致非响应式读取

P1
LoginForm renderer 在 handleDynamicLogin 中调用 getWebsiteAuthState()（LoginFormRenderer.tsx:599）获取 state.buildAuthHeaders() 和 state.setCachedValue()。这是直接调用 store 的 getState()，不经过 React 的响应式系统。如果 buildAuthHeaders 依赖的状态在调用前刚被更新（例如 setConfig 的 useEffect 还没执行），可能读到旧值。
修复：将 buildAuthHeaders 和 setCachedValue 也通过 useWebsiteAuthStore hook 获取，确保响应式。或确保 useEffect 在 handleDynamicLogin 前已执行（React 保证 useEffect 在事件处理前已执行，所以风险较低，但代码可读性应改）。

#13 OAuth/SSO renderer 回调处理时不检查 loginFormId 匹配

P1
OAuth/SSO renderer 在 handleOAuthCallback/handleSSOCallback 中检查 URL 参数后直接执行 token 交换（OAuthButtonRenderer.tsx:101, SSOButtonRenderer.tsx:80）。如果页面上有多个 OAuth/SSO 按钮（指向不同 Provider），所有按钮都会尝试处理同一个回调 URL，可能导致重复 token 交换。LoginForm renderer 的 webcraft-show-login 监听也有类似问题（LoginFormRenderer.tsx:319 注释"接受所有"）。
修复：在 OAuth/SSO 回调处理中，检查 sessionStorage 中的 state 是否由本组件写入（可以在 state 中编码 clientId 前缀）。LoginForm 的 webcraft-show-login 监听应检查 detail.loginFormId 是否匹配自己的 componentId（需要将 componentId 传入 renderer，目前 renderer 拿不到自己的 id）。

P2 级 — 改进建议

#14 store.logout() 的 clearAllCachedValues 只遍历 memoryCache，不扫描 storage 中非 __webcraft_ 前缀的键

P2
store 的 clearAllCachedValues()（websiteAuthStore.ts:678-686）遍历 Object.keys(memoryCache) 并清除对应 storage 键。但如果用户自定义的 tokenKey 不以 __webcraft_ 为前缀（如 my_auth_token），且该键只存在于 storage（未读过所以不在 memoryCache 中），则不会被清除。codegen 侧的 LogoutButton 用 storage.length 遍历解决了这个问题，但 store 侧没有。
修复：store 的 clearAllCachedValues() 追加扫描 storage 中所有以 __webcraft_ 前缀的键（与 codegen 侧 LogoutButton 的做法一致），再额外清除配置的 tokenKey。

#15 OAuthButton renderer 的 resolvedRedirectUri 计算在 useCallback 依赖中每次 render 变化

P2
resolvedRedirectUri（OAuthButtonRenderer.tsx:98）在每次 render 时计算，如果 redirectUri 为空则拼接 window.location.origin + "/callback"。这导致 handleOAuthCallback 的 useCallback 依赖每次 render 变化，useCallback 失去缓存效果。
修复：将 resolvedRedirectUri 用 useMemo 包裹。

#16 UserProfile renderer 同步 userDisplayConfig 到 store 的 useEffect 缺少 cleanup

P2
UserProfile renderer 的 useEffect(() => { setAuthConfig({ userDisplayConfig }); }, [userDisplayConfig, setAuthConfig])（UserProfileRenderer.tsx:31-33）每次 userDisplayConfig 变化都调用 setAuthConfig，但没有 cleanup。如果 UserProfile 被卸载，store 中的 userDisplayConfig 不会被清除，可能影响 clearAllCachedValues 的行为（它依赖 userDisplayConfig 列表保留缓存键）。
修复：在 useEffect 的 cleanup 中调用 setAuthConfig({ userDisplayConfig: [] })，或不做（因为 store 是全局的，UserProfile 卸载后其他组件可能仍需 userDisplayConfig）。

#17 LoginForm codegen 的 performRefresh 重试逻辑使用固定数组 [5, 15, 30]（秒），不可配置

P2
LoginForm codegen 的 performRefresh() 失败后用 var delays = [5, 15, 30] 做指数退避重试（auth.ts:899）。这些延迟值不可配置，且最大重试次数固定为 3 次。HttpAdapter 侧也有独立的重试逻辑（HttpAdapter.ts:304），两套重试逻辑可能冲突。
修复：将重试策略统一到 store 层（或 HttpAdapter 层），移除 LoginForm codegen 中的重复重试逻辑。或将 delays 和 maxRetry 暴露为配置项。

#18 ApiKeyConfig renderer 的 pointerEvents:none 在编辑模式下阻止子组件交互，与"编辑/预览一致"约定矛盾

P2
ApiKeyConfig renderer 编辑模式用 pointerEvents: "none" 替代 disabled（ApiKeyConfigRenderer.tsx:128）。但 pointerEvents:none 会阻止整个 Box 的所有交互，包括 input 的 focus 和 button 的 hover。虽然编辑模式下不需要实际功能，但与 RegisterForm/SSO 的"编辑模式可交互但 disabled"模式不一致。LoginForm 编辑模式用 disabled 而非 pointerEvents。
修复：统一编辑模式禁用方式。建议全部改为 disabled（MUI 组件原生支持），不使用 pointerEvents:none。ApiKeyConfig 之前的修复用 pointerEvents 是为了避免"灰显"，但 MUI 的 disabled 可以通过 sx 覆盖 &.Mui-disabled { opacity: 1 } 来避免灰显。

五、认证闭环路径图

理想认证闭环应覆盖以下 5 条路径。当前实现状态：

路径流程状态断裂点
1. 密码登录 LoginForm → setLogin → auth-state-change → AuthGuard 放行 → UserProfile 显示 ✓ 通畅 —
2. 退出登录 LogoutButton → logout() → clearAllCachedValues → auth-state-change → AuthGuard 拦截 → UserProfile 清空 ✓ 通畅 sessionStorage 中 OAuth/SSO state 残留（#7）
3. 门禁拦截 AuthGuard 未认证 → webcraft-show-login → LoginForm 显示 → 登录成功 → auth-state-change → AuthGuard 放行 + LoginForm 自隐藏 ✓ 通畅 LoginForm 无法匹配 loginFormId（#13）
4. Token 过期刷新 AuthGuard 检测过期 → webcraft-token-expired → LoginForm performRefresh → fetch refreshEndpoint → webcraft-token-refreshed → AuthGuard 放行 ✗ 断裂 expiresAt 键名不匹配（#1）+ HttpAdapter 不监听也不 dispatch（#4, #5）+ memory 隔离（#2）

七、总结

认证闭环当前状态：主链路（登录→守卫→展示→登出）在编辑态和 localStorage/sessionStorage 存储模式下基本通畅。但在以下 3 个维度存在系统性断裂：

① 存储键命名不统一（#1）—— expiresAt vs __webcraft_auth_expires_at，导致 AuthGuard 过期检查永久失效。这是一行代码的修复，但影响面最大。

② memory 存储模式架构缺陷（#2, #3）—— 各 codegen IIFE 的 memoryCache 互相隔离，UserProfile codegen 甚至没有 memoryCache。这不是 bug 而是架构设计缺陷：发布态没有像编辑态的 websiteAuthStore 那样的全局共享 store，需要引入 window.__webcraft_memory_cache 或 fallback 到 sessionStorage。

③ Token 刷新链路断裂（#4, #5）—— HttpAdapter 作为发布态的数据层，既不监听 webcraft-token-expired 也不 dispatch webcraft-token-refreshed，导致 HttpAdapter 触发的刷新与 AuthGuard/UserProfile 完全脱节。当前只有 LoginForm codegen 的 performRefresh() 能处理 token 过期，如果页面没有 LoginForm 组件则刷新链路完全断裂。

修复后预期：第一批 6 个 P0 问题修复后，5 条闭环路径将全部通畅。第二批和第三批可在后续迭代中逐步处理。
